为什么项目拆分为多个 SQLite 数据库文件？

SQLite 默认具有数据库级别的写锁（Write Lock）。若将主业务查询、后台长时间运行的爬虫抓取、定时海投任务，以及 AI Agent 的高频状态持久化全部塞进同一个 job_hunter.db，极易在投递或爬虫写入时发生 sqlite3.OperationalError: database is locked。为此，架构上严格践行「领域读写隔离与独立持久化」原则：

1 · job_hunter.db（业务主库）

承担核心岗位的生命周期流转、AI 打分评级、策略配置与审计流水。由 FastAPI 主服务独占主要写路由。

2 · autopilot.db（海投调度库）

专供后台定时 Cron 任务、桌面端侧车进程（Sidecar）与海投波次独占。即使海投进程阻塞或崩溃，也完全不影响主库查询。

3 · langgraph_checkpoints.db（Agent 记忆库）

LangGraph 状态机执行复杂决策与多工具调用时，每次状态通道写入都伴随大量二进制 BLOB。独立拆库保障主业务不受大对象膨胀影响。

4 · sessions.db（会话管理库）

轻量存储用户人机交互上下文与会话路由，支持会话快速清理与生命周期控制。

跨库隐式外键：三根全局契约键（Contract Keys）

SQLite 不支持跨文件的物理外键约束（Foreign Key across databases），代码层通过三根「全局契约键」实现强一致的逻辑绑定—— 左侧关系图中的实线均为真实数据关联，虚线为业务流叙事。

# 契约键 1 · feishu_record_id —— 全局最核心的岗位业务主键 [job_hunter.db] raw_jobs.feishu_record_id ('recXXXX…') ▲ ├──► [autopilot.db] boss_approvals.record_id（老板放行确认主键） ├──► [autopilot.db] pending_delivery_pool.record_id（海投待发射池主键） └──► [job_hunter.db] action_audit.target_id（操作审计追踪标识） # 契约键 2 · task_id —— 流水线与自动化批次唯一 UUID [job_hunter.db] pipeline_latest_run.task_id ('pipeline_XXXXXXXX') ▲ ├──► [autopilot.db] pending_delivery_pool.task_id（入池批次归属） ├──► [autopilot.db] automation_logs.task_id（波次运行日志索引） └──► [job_hunter.db] agent_task_handles.task_id（进程令牌租约映射） # 契约键 3 · job_link —— 全网抓取物理去重键 [job_hunter.db] raw_jobs.job_link ('https://www.zhipin.com/job_detail/…') ▲ └──► [job_hunter.db] token_log.job_id（单岗位评估消耗审计）

高并发稳定性配置（Concurrency & WAL）

在 app/core/db_bootstrap.py 与 app/automation/db.py 启动引导代码中，显式执行以下配置：

-- 1. 开启 WAL 预写式日志（读写互不阻塞，读并发性能提升数倍） PRAGMA journal_mode = WAL; -- 2. 长繁忙重试超时（防止突发密集写冲突） sqlite3.connect(path, timeout=30.0); -- 3. 自动化同步触发器（raw_jobs 状态变更时自动维护 updated_at） CREATE TRIGGER trg_raw_jobs_status_updated AFTER UPDATE OF process_status ON raw_jobs FOR EACH ROW BEGIN UPDATE raw_jobs SET updated_at = datetime('now', 'localtime') WHERE rowid = OLD.rowid; END;
